TinyGo Conference 2026 in JAPAN

TinyGo 라는 주제로 열린 컨퍼런스에 다녀왔습니다

10 October 202612 min readby gtcheols

개요

지난 싱가포르 고퍼콘 2026 에서 만났던 일본의 tinygo-keeb 모임에서 주최하는 “TinyGo Conference 2026 in JAPAN” 컨퍼런스에 다녀왔습니다. 당시에는 사실 뭔지도 모르고 그냥 가벼운 흥미로 참석했던 워크샵이 기판에 땜질하고, 여기에 올라갈 소프트웨어를 TinyGo 로 개발해서 올리는 워크샵 이었습니다. 그 때 이 워크샵을 주최한 팀이 tinygo-keeb 이라는 일본 팀이었고 이 팀은 일본 내에서 제법 자주 이런 종류의 워크샵을 운영하며 투어를 하는 팀 이었습니다.

개인적으로는 철저하게 소프트웨어 계열의 일을 해온 터라, 이렇게 하드웨어 계열(?) 사람들을 만나는 것도 흥미로웠고, 이런 주제로 이렇게 즐겁게 모여서 온 사람들의 그 분위기가 조금 신기하고, 재미 있어 보여서 친해지고 싶기도 해서, 일본에서 자체적으로 주최한다는 행사에 참석 했습니다.

이 행사는 두 번째로 열렸다고 하고, TinyGo 만을 주제로 하는 컨퍼런스는 다른 나라에는 없다보니 세계 유일(?) 이라고 홍보를 하더군요. 사실 Go 라는 주제도 마이너한데, TinyGo 는 이보다도 더 마이너한 주제라, 이게 되는건가? 싶었는데, 막상 다녀와 보니, 특유의 그 분위기가 재미 있었어요.

좀 아쉬운건, 뒷풀이를 안 가서… 아직도 이 분들과 그다지 친해지지 못했다는..ㅋㅋ

싱가포르에서 솔더링 워크샵을 경험해봐서 이번에는 참여를 안했는데, 이후에 보니 참여할 것을 그랬다는 생각이 계속 드네요. 지난번에는 zero-kb02 이라는 키보드를 만드는 것이었고, 이번에는 명찰로 사용되는 뱃지에 이런저런 기능을 올리는 내용이어서 기념품으로 들고와도 재미 있었을텐데, 아무튼 아쉽네요..

rdon-key

임베디드 멀티코어 환경에서는 뮤텍스(Mutex)를 설정하거나 인터럽트를 금지하더라도 경합(race condition) 문제가 여전히 발생할 수 있습니다. 이는 해당 조치들이 코어의 동작을 제어할 뿐, 코어 외부의 요소까지 제어하는 ​​것은 아니기 때문입니다. 본 세션에서는 TinyGo의 RP2 USB 드라이버에서 실제로 발생했던 경합 사례(PR#5472)를 바탕으로, 처리 순서가 뒤바뀌는 것만으로도 완료 이벤트가 유실되는 메커니즘을 설명합니다. 또한 뮤텍스의 한계를 파악하고, 펌웨어 개발 시 어떤 부분을 중점적으로 점검해야 할지 공유하고자 합니다.

Building a Clock with TinyGo Led Me Down the Rabbit Hole from DNS to TLS

hnw

저는 TinyGo로 간단한 시계를 구현해 보았습니다. M5Stack을 사용하여 NTP로 시간을 가져오고, HTTPS API를 통해 타임존 정보를 얻으면 완성될 예정이었습니다.

하지만 네트워크 통신을 구현하던 중 버그를 발견하여, 임베디드용 Pure Go 네트워크 스택인 ’lneto’에 Pull Request를 보내게 되었습니다. 나아가 lneto를 사용하는 구성에서는 HTTPS를 이용할 수 없다는 사실을 깨닫고, Go 본가의 crypto/tls를 도입해 HTTPS를 구동하는 실험까지 진행했습니다.

이 세션에서는 일련의 시행착오를 통해, TinyGo로 인터넷 통신을 할 때 Wi-Fi, IP, DNS, TCP, HTTP, TLS 각 계층을 누가 담당하는지 정리해 봅니다. 또한, 힙(heap) 사용을 지양하고 고정 길이 버퍼와 메모리 재사용을 철저히 하는 lneto의 설계가 일반적인 Go 프로그래밍과 어떻게 다른지도 소개합니다.

Go 표준 라이브러리를 이용한 HTTPS는 실제로 TLS 1.2/1.3 환경에서 정상적으로 작동했습니다. 하지만 TLS 핸드셰이크 과정에서 힙 사용량이 약 300KB에 달해, RAM이 520KB인 Pico 2 W에서도 거의 한계치에 가까웠습니다. 이러한 결과를 바탕으로 임베디드용 TLS 구현이 왜 필요한지, 그리고 TinyGo에서 HTTPS를 실용적으로 사용하기 위해 무엇이 부족한지 고찰해 봅니다.

PC 환경의 Go에서는 당연하게 사용할 수 있는 네트워크 기능을 TinyGo 환경에서 어떻게 구현하고, 미완성된 부분을 어떻게 만들어 나갈 것인가. 그 과정의 흥미로움을 여러분과 공유하고자 합니다.

Github

단순하게 NTP 와 GPS 정보를 기반으로 동작하는 시계를 만들려고 했다는데, tinyGo 의 패키지에는 crypto/tls 와 같은 패키지가 없어서 일반적인 HTTPS 접속이 안된다는 것을 알게 되었고, 이 원인을 찾아서 해결 해보려고 이런저런 시행착오를 격었지만, 결국 어찌어찌 빌드를 해도 메모리가 부족하거나, 빌드본 크기가 너무 커지는 등의 이슈를 만나서 해결하지 못한것 같네요. 이런 것은 임베디드 환경이라는 제한된 상황, 그리고 사실상 개발 진행중인 비표준 환경인 tinyGo 의 상황을 보여주는 것 같았습니다. 하지만 이렇게 시도하고 고민하는 사람들이 이런 상황을 즐기고 있는 것으로 보여서, 뭔가 신기하면서도 재미 있어 보였습니다.

슬라이드 내 요약

  • TinyGo의 네트워크 관련 부분은 일반적인 Go와 완전히 달라서 흥미롭습니다.
  • TinyGo 라이브러리를 개발할 때는 메모리 절약을 고려해야 해서 재미있습니다.
  • TinyGo에서 TLS를 구현하려면 해야 할 일이 아주 많습니다.
  • TinyGo는 통신 구현도 재미있으니, 여러분도 함께 커밋(commit)해 봅시다!

Rinrin

서론

키보드나 마우스를 PC에 연결하면 별도의 설정 없이도 입력 장치로 사용할 수 있습니다. 그렇다면 장치에서 보낸 입력 신호는 어떤 데이터 형태로 PC에 전달되는 것일까요? 저는 ‘TinyGo Keeb Tour’를 통해 ‘zero-kb02’를 제작하면서 HID를 처음 접하게 되었습니다. 이후 로터리 인코더를 활용한 볼륨 조절 기능 등을 구현하기도 했지만, 정작 HID가 어떤 원리로 작동하는지에 대해서는 깊이 이해하지 못한 채 사용해 왔습니다. 그래서 이번에는 평소 사용하는 Go 언어와 유사한 문법으로 코드를 작성할 수 있는 TinyGo의 구현 사례를 시작점으로 삼아, HID에 대해 한 걸음 더 깊이 알아보려 합니다.

Big / Tiny GOTOOLCHAIN

sivchari

저는 Go와 TinyGo 모두 릴리스 버전이 아닌 소스 코드에서 직접 빌드하여 최신 상태로 사용하고 있습니다. Go의 devel 버전과 TinyGo의 HEAD를 동시에 따라가는 이 생활을 하다 보면, 릴리스 버전만 사용해서는 겪을 수 없는 문제들에 누구보다 먼저 직면하게 됩니다. TinyGo가 Go의 devel 버전을 파싱하지 못하거나, 호환성 매트릭스(compatibility matrix)에서 최신 Go 버전이 배제되거나, 에디터의 gopls 설정이 이를 따라가지 못하는 등의 문제들입니다. 전반부에서는 이러한 문제들을 업스트림 패치(tinygo#4601, tinygo#5078, tinygo.vim#9)를 통해 어떻게 해결해 왔는지 소개합니다. 또한 매트릭스 검사를 우회하는 플래그를 직접 구현한 후, Go 1.26의 표준 라이브러리(stdlib) 삭제(internal/itoa)로 인해 TinyGo가 작동하지 않게 되었던 경험을 바탕으로, ‘매트릭스가 무엇을 보호하고 있었는지’와 Go가 어디까지 호환성을 보장하는지에 대해 이야기합니다. 후반부에서는 반대로 특정 버전의 TinyGo를 간편하게 사용하고 싶은 상황에 대해 다룹니다. 항상 최신 버전을 사용하더라도, 이슈를 재현하기 위해 임의의 버전을 빠르게 설치하고 전환해야 할 때가 있기 때문입니다. 하지만 매번 릴리스된 바이너리를 다운로드하는 것도 번거로운 일이며, 해당 버전의 브랜치에서 소스 코드를 빌드하는 것은 생각만 해도 부담스러운 작업입니다. 이에 제안한 툴체인 관리(tinygo#5202) 방식을 중심으로, ‘TinyGo를 GOTOOLCHAIN으로 활용할 수 없을까?‘라는 검증 과정에서 확인한 Go 툴체인 전환의 내부 구현과 현재의 제약 사항, 그리고 golang.org/dl 패턴으로 구현한 프로토타입인 sivchari/tinygo-dl의 시연을 소개합니다. ‘항상 최신 버전을 사용하고 싶다’는 것과 ‘임의의 버전을 간편하게 사용하고 싶다’는 것은 모두 TinyGo의 툴체인 관리라는 주제로 연결됩니다. Go와 TinyGo 모두 소스 코드에서 빌드하는 입장에서, Go와 TinyGo의 경계에서 어떤 일이 벌어지고 있는지 살펴보고, 당장 내일부터 활용할 수 있는 버전 관리 선택지를 공유하고자 합니다.

go 와 tinyGo 를 모두 소스코드를 내려받아서 빌드하여 사용하는 과정에 go 와 tinyGo 의 버전 호환성 이슈가 항상 있고, 이럴때 특정 go 특정 tinyGo 버전을 변경해서 사용하기 편하게 하는 방법을 고민하다가 golang.org/dl 이라는 repo 를 참고해서 sivchari/tinygo-dl 라는 repo 를 만들어봤다는 내용 입니다. 저는 가능한 검증된 빌드 버전을 사용하는 편이라, 잘 하지 않지만… 이렇게도 사용하시는구나 싶었어요.ㅋ

Observability with TinyGo? Can We Use OpenTelemetry with TinyGo?

Yoshiki Yamaguchi

TinyGo로 구동되는 ESP32-S3 기기에서 OpenTelemetry Collector로 텔레메트리 데이터를 전송하는 실험에 대해 이야기합니다.

일반 Go 환경에서는 OpenTelemetry SDK와 익스포터(exporter)를 사용할 수 있지만, TinyGo와 마이크로컨트롤러 환경에서는 메모리, 네트워크, TLS, 시간 동기화, 버퍼링 등의 제약으로 인해 기존 SDK를 그대로 사용하는 것이 쉽지 않습니다. 이 세션에서는 TinyGo로 OTLP/HTTP의 최소 구성을 구현하고, RSSI, 가동 시간(uptime), 센서 값, 전송 성공/실패 등의 데이터를 Collector로 전송하여 시각화하는 데모를 시연합니다.

OpenTelemetry의 모든 기능을 포함하는 것이 아니라, TinyGo로 표준적인 관측 가능성(observability) 파이프라인을 어디까지 구현할 수 있는지 검증하고, 구현상의 제약 사항과 Collector 측으로 위임해야 할 처리 내용을 공유합니다. 시간이 허락한다면 ESP32-C3로 이식할 때 발생하는 제약 사항의 차이에 대해서도 다룰 예정입니다.

저는 서버에서 로그를 수집하거나 상태 정보와 같은 시계열 데이터를 수집하는 용도로 접근했던 OpenTelemetry 를, 임베디드 장치의 센서 등에서 수집된 시계열 데이터를 수집하는 용도로 접근하는 내용 입니다.

최근 tinyGo 가 ESP32 의 WiFi를 지원하면서 이 장비에서 수집된 시계열 데이터를 서버에 전송하는 exporter 를 tinyGo 로 구현하는 PoC를 진행 했다고 합니다.

OpenTelemetry 라는게, 특정 벤더나 장치, 기술등에 얽매이지 않고 사용할 수 있도록 한다는게 목표라서, 서버간 통신이 아닌 임베디드 장치와의 통신도 이미 당연히 잘 되고 있겠구나 했는데, tinyGo 로 구현해보니 실상은 쉽지 않았다는 이야기 입니다.

슬라이드의 결론

  • OTel Go SDK를 사용할 수 없는 원인은 메모리 제한이 아니라, 호스트 OS에 대한 의존성과 reflect 기능이 구현되어 있지 않기 때문입니다.
  • OTLP 스키마는 사용할 수 있습니다. encoding/json, 직접 구현한 HTTP 클라이언트, 그리고 SNTP를 통해 통신이 가능합니다.
  • 마이크로컨트롤러 환경에서 문제가 되는 것은 메모리 용량 자체보다는, 전송할 때마다 발생하는 메모리 할당과 고루틴(goroutine) 스택 문제입니다.
  • 디바이스는 해당 환경에서만 알 수 있는 정보만 전송하고, TLS 처리나 속성(attribute) 추가는 Collector에 맡깁니다.
  • Collector 이후 단계는 서버에서 사용하는 OpenTelemetry와 동일한 파이프라인을 거칩니다.

TinyGo Keeb Tour에서 zero-kb02를 조립했지만 제대로 활용하지 못하고 계신 분들을 위해, 초보자의 시선에서 저만의 활용법을 소개해 드립니다. 워크숍에서는 샘플을 구동하는 단계까지 진행했지만, 그 이후에 무엇을 만들어야 할지 막막했었습니다. 그러던 중 Codex Micro를 접하게 되었고, TinyGo와 zero-kb02를 활용해서 Codex용 물리 UI와 유사한 것을 만들 수 있지 않을까 하는 아이디어를 떠올렸습니다. 이번 발표에서는 LED, OLED, 키 입력, USB 통신을 조합하여 워크숍에서 사용한 기판을 저만의 도구로 발전시켜 나간 과정을 소개합니다. 구현 과정에서 겪었던 어려움, 라이브러리 활용법, 실기기에서의 테스트 방법 등을 공유할 예정입니다. 워크숍 이후 무엇을 만들지 고민하시는 분들께, 자신만의 오리지널 키보드 제작을 시작하는 계기가 되기를 바랍니다.

zero-kb02 를 어디에 사용할까 하다가, codex micro 라는 제품에 대해 알게 되었는데, 뭔가 비슷한 구성이라는 생각이 들어서 이와 유사한 걸 만들어보게 되었다는 내용 입니다.

makki

OpenAI의 AI 에이전트 컨트롤러인 ‘Codex Micro’는 LED로 빛나는 십여 개의 키와 다이얼, 조이스틱을 갖추고 있습니다. ‘TinyGo Keeb Tour’에서 제작하는 ‘zero-kb02’와 아주 흡사하죠. 그래서 ‘zero-kb02’를 AI 에이전트 컨트롤러로 활용할 수 있는 ‘zero-micro’를 만들어 보았습니다. https://github.com/makiuchi-d/zero-micro

작업 완료 시 불빛으로 알림을 주고, 승인이 필요할 때는 명령어를 표시하며 버튼으로 승인 또는 거절을 할 수 있어 화면을 직접 볼 필요가 없습니다. 게다가 키 입력이 tmux로 전달되므로 터미널이 백그라운드에 있어도 문제없습니다. 에디터로 작업하면서 조이스틱으로 에이전트의 출력을 확인하는 등, 상상했던 것보다 훨씬 편리합니다.

훅(hook)을 교체하면 Claude 외의 다른 서비스도 지원할 수 있을 것입니다. Codex Micro처럼 여러 세션을 전환하는 기능도 구현 가능해 보입니다. 지금부터 이 ‘zero-micro’의 설계 및 구현 개요에 대해 말씀드리겠습니다.

뭔가 웃지기만 이전 라이트닝 토크 세션과 거의 같은 주제 입니다. ㅋㅋ. 지난 싱가포르 고퍼콘에서 워크샵에서 솔더링(땜질?)을 많이 도와주셨던 makki 상의 발표 였네요.

[LT] Something Small, Cute, and Go

Yasutaka Kato

직접 제작한 가정용 IoT 기기는 일단 운용을 시작하면 유지보수나 리팩토링을 뒤로 미루기 쉽지 않나요? 그러다 보면 어느새 라이브러리 노후화, 언어 버전의 EOL(지원 종료), 하드코딩 누적과 같은 기술 부채가 쌓이게 됩니다. 저는 10년 전 Python으로 구현해 매년 여름마다 가동 중인 가정용 수조 쿨러를 소재로, TinyGo와 Claude Code를 조합해 리팩토링을 수행한 사례를 소개하고자 합니다. ① 방치된 IoT 기기의 기술 부채: 10년 전 Python으로 구현한 수조 쿨러가 유지보수 없이 매년 계속 가동되고 있는 사례를 소개합니다. 어떤 라이브러리를 설치했는지조차 잊어버렸고, Python 자체도 EOL을 맞이했으며, 코드 곳곳에는 하드코딩이 남아 있었습니다. ② TinyGo가 열어준 리팩토링의 길: 싱글 바이너리의 간편함에 매료된 이후 7~8년 동안 Go 언어를 사용해 왔으며, 개인 OSS도 대부분 Go로 구현했습니다. 이전에는 IoT 분야에서 선택지가 아니었던 Go가 TinyGo의 등장으로 현실적인 선택지가 되었습니다. 지금이야말로 리팩토링을 시작할 때입니다! ③ Claude Code를 활용한 리팩토링과 그 이후: 기존 Python 구현을 바탕으로 Claude Code를 활용해 리팩토링을 진행했습니다. 이미 검증된 기존 코드가 있었기에 구현이 무너지지 않고 깔끔한 코드로 완성할 수 있었습니다. 수많은 의존 라이브러리는 작고 귀여운 하나의 싱글 바이너리로 다시 태어났으며, 경량화를 통해 확보된 여유 공간은 새로운 기능을 추가할 수 있는 발판이 되었습니다. 집에 잠들어 있는 오래된 IoT 기기의 리팩토링, 꼭 TinyGo로 시도해 보세요.

なんか小さくてかわいいGoなやつ | ドクセル

오래전에 Python 으로 만들었던 코드가 신기하게도 아직 잘 돌아가고 있긴 했는데, 이걸 최신화 하려고 하면서 tinyGo 로 다시 구현했고 이건 Claude Code 의 도움을 바아서 진행했더니, 빠르고 효과적이었다는 내용 이었습니다.
